## Abstract

The Helix Memory Corridor is a file based hybrid memory system for persistent AI agents. It stores durable memory as immutable Markdown events on a plain file spine, and retrieves that memory through four independent retrieval arms fused into one ranking: a semantic arm using all-MiniLM-L6-v2 embeddings, a BM25 keyword arm, a graph arm using Personalized PageRank over a heuristically extracted entity graph, and a temporal arm keyed to date windows in the query. Fusion is Reciprocal Rank Fusion with constant 60. A multiplicative re-rank then applies entity based importance and a 180 day recency decay. A bi-temporal validity layer sits in front of all four arms: every fact carries a valid time interval and a recorded time, corrections close earlier intervals by explicit supersession, and a lookup can ask what is true now, what was true at an earlier valid time, or what was known at an earlier recorded time.

No language model runs anywhere in the retrieval path. There is no database server, no required network service, and no API key on the core path. The corpus is a directory tree of human readable files that an operator can inspect, copy, back up, and repair with ordinary tools. Integrity is enforced by hashes: each stored event carries three SHA-256 digests, validation recomputes them, and a single mismatch is treated as a corpus level event rather than a local blemish. Derived indexes are generations, gated by manifests that bind them to an exact document set and an exact model revision, and every generation is regenerable from the files, because the files are the source of truth and nothing else is.

This paper describes the whole system as it stands at version 0.3.1, the live install: the problem it answers, its design principles, the corpus format, the immutable event layer, the validity model, the retrieval pipeline in detail, the command line and operational practice around it, its governance model for multi agent use, what can and cannot be measured about it today, its position relative to related systems, its known limitations, and its roadmap. The roadmap's next step, version 0.3.2, is a proposed and unbuilt trace layer, nicknamed the spider, which would persist the retrieval provenance the current system computes and discards, and add a read only integrity crawler over the corpus. It is presented as one chapter of this paper, clearly marked as a proposal, because that is its correct proportion: the corridor is the system, and the spider is its next increment.

## 1. The problem: memory that survives the session

### 1.1 Agents forget by construction

1. A conversational AI agent's working memory is its context window. Context windows compact, sessions end, processes restart, and providers rotate. Anything the agent knew only inside a session is gone when the session closes, unless something outside the session kept it.
2. The failure is not subtle. Decisions made on Monday are re-litigated on Wednesday because the record of the decision, and of the reasoning and corrections around it, never left the chat that produced it. An agent that cannot check its own prior work will confidently repeat it, contradict it, or redo it, and the operator pays for all three.
3. Persistence alone is not the hard part. Writing notes is easy. The hard parts are retrieval and truth maintenance: finding the right note among thousands, under paraphrase, under time pressure, and knowing which of two contradictory notes is the current one.

### 1.2 Why plain notes fail

1. Plain notes, meaning an unstructured pile of Markdown or text files with at most keyword search, fail on retrieval first. Keyword search finds exact terms and misses everything else: the paraphrase, the synonym, the entry that shares the people and the project but not the wording of the question. As a corpus grows past a few hundred entries, the entries that keyword search misses are not rare cases. They are most of the corpus's value.
2. Plain notes fail on correction second. In a working memory, facts change: a price is corrected, a decision is reversed, a name was wrong. If the correction is just another note, both versions sit in the corpus with equal standing, and any retrieval that finds the older one first returns a stale fact with full confidence. Appending corrections without a validity model manufactures confident errors at scale.
3. Plain notes fail on time third. Agent memory questions are saturated with time: what happened last week, what was the status before the correction, what did we know when we made that call. A store that cannot separate when a fact was true from when it was recorded cannot answer any of these honestly.

### 1.3 Why a plain vector store fails

1. A vector database over note chunks fixes paraphrase retrieval and nothing else. It returns the stale fact as happily as the corrected one, because embedding similarity has no concept of supersession. Chunking severs entries from their metadata, their authorship, and their correction links.
2. A vector store is also opaque in operation. The corpus lives inside a binary store that the operator cannot read, diff, grep, or repair with ordinary tools. When (not if) an embedding generation is built against the wrong model revision or a partial document set, the failure is silent and the diagnosis is archaeology inside someone else's file format.
3. Finally, a hosted vector service moves the memory off the operator's machine. For a personal or small team memory, which contains exactly the material its owner least wants replicated to third parties, that is a standing exposure accepted in exchange for convenience the workload does not need. The corpora at issue are thousands of documents, not billions. Local methods are not a compromise at this scale. They are sufficient, and they keep custody simple.

### 1.4 Correction and supersession as first class needs

1. The requirements that drive this design, stated plainly:
   1. Memory must persist outside any session, in a form a human can read and audit directly.
   2. Retrieval must combine lexical, semantic, relational, and temporal evidence, because no single signal survives contact with real questions.
   3. Correction must be a structural operation, not a prose convention: a correction must change what default retrieval returns, while preserving the corrected record and the ability to ask what was believed before.
   4. Time must be two dimensional: the time a fact was in effect, and the time the system learned it.
   5. Integrity must be checkable: the system must be able to prove a stored record is the record that was written, and must react loudly, not silently, when it cannot.
   6. The retrieval path must be deterministic and inspectable: no language model between the question and the ranking, so that a surprising result can be explained from scores, ranks, and windows rather than from a model's mood.
   7. Everything derived must be regenerable from the source files, so that no index failure is ever a memory loss.

## 2. Design principles

1. Files are the source of truth. The corpus is a directory tree of Markdown files. Indexes, embeddings, graphs, and validity tables are derived artefacts, cached under a separate state directory, and any of them can be deleted and rebuilt without losing a single memory. If a derived artefact and a file disagree, the file wins by definition.
2. Append only at the event layer. New knowledge is a new event. Corrections are new events that name what they supersede. Nothing is edited in place and nothing is deleted by the system, so the history of what was believed, and when it changed, is itself part of the memory.
3. No language model in the retrieval path. Retrieval is arithmetic: token statistics, vector geometry, graph diffusion, date windows, and rank fusion. This is a deliberate constraint, not an omission. It makes results reproducible, makes failures diagnosable, keeps operating cost at zero per lookup, and keeps the system fully functional offline. A small embedding model is used, and it is a geometry engine, not a reasoner: it maps text to points. Section 6.1 is precise about what it does and does not do.
4. Local first. The reference deployment runs entirely on one machine: files on local disk, embeddings computed on CPU, indexes as local files and a local embedded vector store. The core path needs no network, no account, and no key. Portability follows: the whole corpus is a folder, and moving the memory is copying the folder.
5. Integrity by hash, failure by exception. Stored events carry cryptographic digests over their content and metadata. Validation recomputes the digests and raises on mismatch. The collector that feeds indexing refuses to downgrade a malformed stored record into unchecked legacy text. The system's posture is that silent tolerance of corruption is worse than a loud stop, because a memory system that quietly serves altered records has failed at its one job. Section 7.4 describes the operational cost of that posture and the practice that has grown around it.
6. Explicit over inferred, wherever truth is at stake. Supersession happens only when a record names the record it supersedes. A temporal arm that finds no date in the query abstains rather than guessing. A graph fallback announces itself in the health diagnostics rather than quietly returning weaker results. The system prefers a visible absence to a fabricated presence, a preference that recurs in every layer and in the 0.3.2 proposal.
7. Every lookup leaves a receipt. Recall returns diagnostics with its results: the source generation digest, the observation time, the count of eligible documents, the count validity excluded, and a per arm health entry. A result without provenance is treated as a defect, because an operator who cannot tell which generation a result came from cannot tell whether to trust it.
8. Human readable at every layer a human might touch. Events are Markdown with a one line structured header. Index manifests are JSON. Handoff state is a marked block inside an HTML file a human already reads. There is no layer of the system whose contents require the system itself to interpret.

## 3. The corpus: a spine of structured entries

### 3.1 Layout

1. The corpus is a directory tree, called a spine in the reference deployment. At the top level sit subject categories; the reference deployment uses seven, spanning system rules, legal, finance, work, projects, personal, and media material. The system itself is not wedded to any particular set: the collector treats any category directory as a scope, and the public release generalized the layout so any Markdown directory with category subdirectories works. A fixed category scheme matters operationally, not architecturally: it gives writers a shared map of where a fact belongs, and gives scoped queries a meaningful boundary.
2. Inside each category, entries live in a periodic entries folder, alongside a per category index folder holding a human maintained index file of key facts for that category. The collector walks the tree, reads root Markdown and category subdirectories recursively, splits files on their section structure, and assigns each document a stable ID with an explicit source path. Stability matters: an ID that drifts when a new file lands would silently break every correction link and every citation that points at it.
3. Scale, stated as a dated snapshot rather than a design constant: in November 2026 the reference corpus held about 2,950 periodic entries and about 2,960 Markdown files in total, and it grows by multiple entries per day. Every design decision in this paper should be read against that scale: large enough that no human holds it in their head, small enough that full corpus operations (rebuilding every index, hashing every record) are measured in minutes, not hours.

### 3.2 The writing rhythm: pulses and handoffs

1. Entries are written on a rhythm, not at random. The reference deployment's writers produce periodic entries (pulses) that record what happened in an interval: decisions taken, results verified, state changed, blockers found. Each pulse is paired with a handoff entry that carries the forward state: what is running, what is waiting, what the next action is. A pulse without its paired handoff is treated as an incomplete record, because the pulse says what happened and the handoff says what it means for whoever picks the work up next.
2. Alongside the entry stream sit two kinds of standing documents. Per category index files hold the quick facts an operator or agent needs without a search. A single living handoff document holds the current cross cutting state, including a marked resume block (goal, last verified step, evidence, next action, blocker, approvals, last event ID) that is updated in place under revision control, so that any session, human or agent, can resume work without reconstructing it from the entry stream. The resume block is data. Reading it grants no authority and executes nothing, a boundary the public architecture document states explicitly.
3. The rhythm is a convention layered on the format, and the paper separates the two deliberately. The format (section 4) is what the software enforces: headers, hashes, readback. The rhythm is what the operators enforce: write at transitions, pair pulse with handoff, never let a correction exist only in a chat. Systems adopting the format without the rhythm will get correct retrieval over an incomplete memory, which is the most dangerous kind.

### 3.3 What an entry contains

1. An entry is Markdown prose, written to be read by a human first. Structure inside the prose is light: headed sections, numbered lists for enumerations, and explicit statements of what happened, why, and what changed. Entries record provenance as they go: who acted, on what evidence, and what remains unverified. The corpus's usefulness in practice has depended less on any retrieval feature than on this discipline: entries that state their own confidence make retrieval results interpretable, and entries that do not, do not, no matter how good the ranking is.
2. Entries written as stored events (section 4) carry a one line machine readable header. Older and lighter entries, including per category index files and legacy notes, are plain Markdown. The collector distinguishes the two: stored records are validated strictly, legacy Markdown is indexed as text without the event guarantees. The two classes coexist in one corpus, and section 11 is honest about the seam.

## 4. The event layer: immutable, hashed, idempotent

### 4.1 The header

1. A stored event is a Markdown file whose first line is a JSON header. In the live 0.3.1 store format (schema version 1) the header carries: a canonical UUID event_id; recorded_at, the timestamp the event was written; valid_from, the time the stated fact takes effect; area, the corpus scope; actor, the full identifier of the writer; task_id, grouping events that belong to one thread of work; kind (for example a plain record or a correction); a supersedes list naming the event IDs this event closes; and three SHA-256 digests described below.
2. The header is one line by design. It can be read with the simplest tools, it survives copy and paste, it does not disturb the Markdown below it, and a human opening the file sees the metadata before the prose, which is the correct order for judging a record.

### 4.2 The three hashes

1. payload_sha256 digests the event's content as a canonical object: validation rebuilds a canonical JSON object from the header fields plus the body and hashes that, so the digest binds metadata and prose together. Changing a word of the body, or a field of the header, changes the payload digest.
2. record_sha256 digests the record as stored, the check that the file on disk is the file the writer produced.
3. idempotency_key_hash digests the writer supplied idempotency key. Capture is an explicit operation, and explicit operations get retried, by schedulers, by agents recovering from interruption, by humans reissuing a command. A repeated capture with the same idempotency key returns the existing event instead of writing a twin. The same key presented with different content is an error, not an overwrite: the system treats it as evidence that one of the two writes is not what its author intended, and refuses to guess which.

### 4.3 Capture discipline

1. The store's write path is deliberately ceremonial. Writing an event means: compose the record, write it, flush it to disk, read it back, verify the readback against the digests, and only then report the capture as durable. The receipt an author receives distinguishes these states. A capture that was composed but not read back verified is not reported as stored, because in a memory system the difference between "probably wrote it" and "verified it is there" is the difference between a memory and a rumor.
2. Writers coordinate with local file locks. Concurrent writers on one machine are supported; the locks are cooperative and local, and the public architecture document is explicit that they do not fence unrelated writers, do not replicate state, and do not amount to distributed coordination. The system's answer to multi machine use is the verified mirror (section 7.3), not a lock protocol.
3. Immutability is enforced socially by the format and mechanically by validation. There is no update operation and no delete operation in the store's vocabulary. The only way an event's content changes is if a file is altered outside the system, and that is precisely what the digests exist to detect.

### 4.4 Validation posture

1. Validation is strict and loud. Recomputing a payload digest that does not match raises an integrity error. The collector, which walks the corpus to feed the indexes, refuses to downgrade a malformed stored record into unchecked legacy Markdown: it validates, and it raises. One corrupt stored file therefore does not degrade retrieval quality by a fraction. It stops collection for the whole corpus until the file is dealt with.
2. That posture is a trade, and this paper does not hide it. The alternative, tolerating the bad file and indexing around it, keeps the system answering questions while one of its records is not what it claims to be, and gives no surface on which the discrepancy must ever be confronted. The corridor chooses the loud stop, and pays for it in operational practice (section 7.4): quarantine the file outside the corpus, keep the corpus answering, repair under human ruling. The November 2026 incident in section 7.4 is this posture meeting reality.
3. A second strictness lives in the validity index build: a supersession whose effective date predates the record it claims to close raises and fails the build. An inconsistent correction history is treated as a defect to fix at the source, not a condition to paper over at query time.

## 5. Bi-temporal validity: two clocks on every fact

### 5.1 Valid time and recorded time

1. Every stored fact lives on two timelines. Valid time is when the fact was in effect in the world: a grant amount was one figure until the decision letter arrived, then another. Recorded time is when the system learned it: the entry was written when it was written, and not before. Conflating the two is the root error of most agent memory: a correction recorded today about last month makes naive systems believe either that last month's decisions were made with today's knowledge, or that today's knowledge is only as old as the event it corrects. Both are false, and both produce bad answers to ordinary questions.
2. The corridor keeps the two separate in the format and in the query. Each event carries valid_from in its header and recorded_at alongside it. A supersession closes the earlier event's window: the earlier record gains an implicit valid_until equal to the correction's effective time. Windows are half open intervals of belief: within its window, a record is what the system stands behind.

### 5.2 Supersession: corrections that change the default answer

1. Supersession is explicit only. A window closes when, and only when, a later record's supersedes list names the earlier record's event ID. Shared names, similar wording, and prose claims like "updated" never close anything by themselves. This is the single most consequential rule in the system, and the public line hardened it deliberately: the earlier design generation experimented with heuristic closure (shared entities plus correction keywords in prose), and the 0.3.0 retention repair replaced it with explicit timestamped supersession, because a heuristic that occasionally closes the wrong fact is worse than a discipline that occasionally leaves a closure unwritten. An unclosed stale fact can be found and closed. A wrongly closed true fact is invisible.
2. Default retrieval respects validity before it ranks. In the default path, the eligible set for a lookup is computed first, for the requested valid time and recorded time, and every arm runs against that eligible view. A superseded entry therefore cannot appear in results, and, just as importantly, cannot crowd an eligible entry out of an arm's capped candidate list. The correction changes the world the arms search, not merely the order of what they return.
3. The corrected record is not deleted, hidden from the record, or rewritten. It is stepped over by default and fully present on request. Dedup mode (section 6.6) deliberately suspends the validity filter, because consolidation work needs to see the twins, including the superseded ones. Point in time queries use the same machinery in the other direction.

### 5.3 Three questions, three different answers

1. What is true now: the default lookup, valid time now, recorded time now.
2. What was true then (as_of): set the valid time to a past date. The system returns the records whose windows covered that date, including records since corrected. This is the query that reconstructs the world a past decision was made in.
3. What was known then (known_at): additionally cap recorded time. A correction recorded last week about last month does not leak into a view of what the system knew last month. The public architecture states the rule plainly: known_at prevents future recorded corrections leaking into a historical view. Together, as_of and known_at give the corridor a property most agent memory lacks entirely: it can distinguish "we were wrong" from "we could not have known", which is the difference between a process failure and an information failure, and the two need different fixes.

### 5.4 Known limits of the validity layer

1. Broken links are silent. If a record's supersedes list names an event ID that does not exist in the corpus, the index build keeps the reference as unresolved and moves on. No surface reports it. A live correction pointing nowhere looks, to every current tool, exactly like a correct correction. This is the validity layer's known blind spot, and it is one of the two findings that motivate the integrity crawler proposed in section 12.
2. Closure depends on writers doing it. Explicit supersession is only as complete as the writing discipline behind it (section 8). A correction written without its supersedes list is a second fact, not a correction, and default retrieval will surface both. The system can detect some of these after the fact (near duplicate detection, section 6.6), but detection is a prompt for a human ruling, not an automatic closure.
3. Windows are only as precise as their timestamps. Legacy records with date only or filename derived times resolve to documented UTC boundaries in the public line; undated records stay undated rather than being silently treated as current. A corpus with mixed precision gets mixed precision answers, and the diagnostics say so rather than smoothing it over.

## 6. Retrieval: four arms, one fusion, no model in the loop

### 6.0 Pipeline overview

1. A recall begins by rereading the source. The collector snapshots the current corpus, fingerprints the selected scope, and the lookup's diagnostics record that generation digest and the observation time. Cached index state is keyed to content and scope, so an appended entry invalidates the warm state it affects: a fresh fact cannot hide behind a stale cache.
2. The four arms then run, in parallel threads in the library implementation, each returning a ranked candidate list capped per arm (default cap 25). Validity has already restricted the eligible view (section 5.2). The arms' lists are fused, re-ranked, sliced to the requested top_k, and hydrated: the returned text comes from this call's source snapshot, not from a cached excerpt, so what the reader sees is the file as it stands now.
3. Every stage's byproducts are kept in the result objects: per arm ranks, per arm raw scores, fusion score, importance and recency factors, final score and rank. Today those byproducts are returned to the caller and then, in most deployments, dropped. What 0.3.2 proposes to do with them is section 12's subject.

### 6.1 The semantic arm: geometry, honestly labelled

1. The semantic arm embeds text with all-MiniLM-L6-v2, a small sentence embedding model: 384 dimensional vectors, roughly 90 MB, CPU friendly, downloaded once and cached. Each document and each query becomes a point in that vector space, and the arm ranks by proximity: texts whose meanings are similar land near each other. Storage is an embedded vector store (ChromaDB), one collection per category, HNSW index, cosine space. The arm's score for a document is max(0, 1 minus cosine distance) to the query vector.
2. Precision about what this is matters, because the arm is routinely over credited. MiniLM does not reason, plan, summarize, verify, or decide. It contributes geometry: a paraphrase detector of genuine but narrow power. It finds the entry about certification progress when the question says cert grind. It cannot find the entry whose relevance depends on a fact stated nowhere in its text, and it cannot tell a true statement from a false one. The system's other arms exist precisely because this one, alone, is not enough, and the design treats its output as one vote among four.
3. Generations are the arm's integrity mechanism. A semantic generation is gated by a manifest (version 3 in the live install) recording the model name, the pinned model revision (the live install pins revision 1110a243fdf4706b3f48f1d95db1a4f5529b4d41 of all-MiniLM-L6-v2), a corpus fingerprint, and the exact document ID set the generation was built from. A generation is reused only when manifest and collection contents match exactly. A generation built against a different model revision, or a partial corpus, is therefore not silently served: it is rebuilt or the arm reports degraded. The 0.3.1 release exists largely because of this arm: its predecessor re-embedded the corpus per call in a way that made opt in semantic use impractical, and 0.3.1's verified behavior is that recall reuses the built generation with zero document re-encodes on a fresh process.
4. The arm is opt in. The core path never downloads a model and never requires one. In the reference deployment's command line shim, the default invocation runs the three core arms and semantic joins only when explicitly requested, for a practical reason: most operational lookups are about names, decisions, and dates, where the core arms are strong and the model load is pure latency. The diagnostics report the arm's state either way (ok, degraded, failed, disabled), so a result set that lacks semantic input says so on its face.

### 6.2 The BM25 arm: the literal words

1. The BM25 arm is standard rank BM25 keyword search over the current source snapshot: tokenized text (lowercase alphanumeric tokens in the public implementation), no learned component. Its virtues are the semantic arm's defects, inverted. It is exact about names, identifiers, amounts, and quoted phrases. It is deterministic to the point of boredom. And it is blind to paraphrase, which is why it votes rather than rules.
2. Operationally the arm oversamples before scope filtering so that a category restricted query still returns a full candidate list, and its cache stores tokenized corpus state while texts are re-read from source on load, keeping the freshness rule of section 6.0 intact.

### 6.3 The graph arm: entities, co-occurrence, and Personalized PageRank

1. The graph arm exists to find what neither wording nor meaning similarity can: the entry that is relevant because of who and what it shares with the question. Its construction is deliberately primitive. Entities are extracted by heuristic regular expressions only: capitalized phrases of up to four words, all caps tokens, and quoted phrases, filtered by a stop list of sentence starters and calendar words. There is no named entity model, no entity resolution service, and no learned component. Two entities appearing in the same document gain an undirected co-occurrence edge weighted by count, built per category. The result is a bipartite graph of entity nodes and document nodes.
2. At query time, the question is matched against entity names by substring scoring, capped at ten seed entities. Ranking is Personalized PageRank, damping factor 0.85, over the bipartite graph, with seed mass weighted by entity specificity, defined as 1 divided by log(1 plus degree): a rare entity pulls harder than a hub entity that co-occurs with everything. Returned document scores are multiplied by the mean specificity of their entities, for the same reason. The intuition is the one HippoRAG established and this system adopts: in a memory corpus, the distinctive shared entity is the signal, and the ubiquitous one is the noise.
3. Degradation is announced, not hidden. If the graph library or its PageRank dependency is unavailable, the arm falls back to a one to two hop walk over the same graph and records the fallback, with its reason, in the health diagnostics. A reader of the receipt can always tell whether the graph number they are looking at came from full diffusion or from the walk.
4. The arm's known waste is the subject of section 12: PageRank assigns a score to every node in the graph, entities included, and the extraction step keeps only document nodes. The entity activation map, which entities lit up, how strongly, and through which seeds, is computed in full on every lookup and discarded. Nothing about the arm's results would change if it were kept. It is simply not kept, yet.

### 6.4 The temporal arm: dates as evidence

1. The temporal arm extracts a date window from the query when one is present: explicit dates, relative expressions (yesterday, last week, since Monday), and month references, via pattern matching with a date parsing fallback. Documents inside the window are boosted; in the public implementation, documents inside score 1.0, scores decay with distance outside the window over a 30 day scale, and undated documents score a neutral 0.5 rather than being punished for the corpus's bookkeeping.
2. When the query carries no date, the arm abstains, returns nothing, and the health receipt records abstention as a first class state. An abstaining arm is information: it tells the reader that the ranking they are looking at had no temporal evidence to work with, which is frequently the true explanation for a surprising result.

### 6.5 Fusion: Reciprocal Rank Fusion

1. The four arms produce scores in incomparable currencies: cosine proximity, BM25 statistics, diffusion probability, window membership. The fusion therefore ignores raw scores and combines ranks. Reciprocal Rank Fusion with constant k of 60 gives each document the sum over arms of 1 divided by (60 plus its rank in that arm). A document ranked second by three arms (3 times 1/62, about 0.048) beats a document ranked first by one arm alone (1/61, about 0.016). Consensus wins by construction, which is the behavior a memory system wants: the entry that lexical, relational, and temporal evidence all point at is very likely the entry the question is about. The constant follows Cormack et al. and the Hindsight lineage the design adapts; the architecture notes say, in terms, do not tune it.
2. Per arm caps (default 25) are applied before fusion, so no single enthusiastic arm can flood the merged pool, which at current caps holds at most about 100 candidates before the final slice.

### 6.6 Dedup mode: the second fusion

1. Dedup mode exists to find near duplicates for consolidation, and it changes two things. Fusion becomes round robin interleave: rank 1 of each arm in turn, then rank 2 of each, de-duplicated, guaranteeing every arm's top hit a slot. And the validity filter and re-rank are suspended, because the quarry is the old twin, including the superseded one.
2. The reason is a documented failure of the default path for this job: the near identical twin of a new entry is typically semantic rank 1 but lexically distant, so RRF averages it below the cut and the writer, seeing nothing, writes a duplicate. Interleave never buries an arm's first choice. Dedup mode is the system's admission that "find the current truth" and "find everything similar" are different questions deserving different machinery.

### 6.7 The multiplicative re-rank

1. After fusion, surviving candidates are re-ranked multiplicatively: final score equals RRF score times (1 plus log(1 plus distinct entity count)) times exp(minus age in days divided by 180). The first factor is importance: an entry dense with distinct entities is usually a substantive record rather than a passing mention. The second is recency decay on a 180 day scale: gentle enough that a three month old decision is barely penalized, firm enough that today's correction outranks last month's status note when their fusion scores are close. Undated documents take recency factor 1.0, no penalty.
2. Both factors are recorded in candidate metadata alongside the fusion score and the per arm ranks, so the final ordering is fully decomposable after the fact. A reader who disagrees with a ranking can see exactly which factor moved it, which is the practical difference between a ranking a team can calibrate and one it can only obey.

### 6.8 The diagnostics receipt

1. With diagnostics on, which the current command line path uses by default, recall returns: the source generation digest, the source observation time, the eligible document count, how many documents validity excluded, per arm status with fallback reasons, and the as_of and known_at the lookup ran under. The library serializes the full result dataclasses to JSON for callers that want them.
2. The receipt is the system's standing answer to the only question that matters after a surprising result: what exactly did you search, and in what state was it. Section 9 returns to what the receipt does not yet make measurable.

## 7. The command line and operations

### 7.1 The hmc surface

1. The installed CLI (command name hmc) exposes the system's operations as subcommands: index (build or refresh the derived indexes), recall (query current source with freshness diagnostics), latest (read recent source events for a task directly, bypassing optional indexes), remember (append a durable event and verify readback), resume (read or update the single handoff resume block under revision checks), mirror (create a complete, verified, non deleting backup generation), verify (verify every file in a saved generation), restore (restore a generation into a new or empty directory only), and doctor (inspect local source and configuration without changing anything). A version flag reports the installed package version, 0.3.1 in the reference deployment.
2. The reference deployment wraps the installed CLI in a small shim preserving an older, question first interface the operators had standardized on: a bare question runs recall with the core arms; flags restrict to one category, set top_k, add the semantic arm, set an as_of date, request dedup mode, or trigger a rebuild. The shim also pins the environment for offline operation (the embedding model is warm cached locally and the runtime is told not to reach for the network), a small but telling operational detail: a local first system has to defend its locality against libraries that assume connectivity.
3. The newest subcommands pass through the shim untouched. The two interfaces coexist because they serve two habits: the question first form for the daily "check the corridor before acting" reflex, and the explicit subcommands for capture, recovery, and backup operations where ceremony is the point.

### 7.2 Rebuilds and generations

1. Derived state is rebuilt, never patched. The index operation rebuilds the BM25 cache, the per category entity graphs, the validity index, and, unless told otherwise, the semantic generations. On the reference corpus the full rebuild is a minutes scale job. The operating rule is simple: rebuild when recall feels stale, and rebuild after any bulk change to the corpus, because the generation manifests make a correct rebuild cheap to verify and an incorrect one impossible to mistake for a correct one.
2. Each index family carries its own generation identity. BM25 caches are keyed to content and scope. Semantic generations are manifest gated as described in section 6.1. Validity generations record the supersession state they were built from. The practical consequence is that staleness is a per family condition with a per family remedy, a distinction section 12's crawler proposal leans on: a stale family is not a corrupt corpus, and confusing the two wastes the scarcest resource in operations, which is a calm diagnosis.

### 7.3 Mirrors and the writer directory

1. Backup is a first class operation, not a sync folder hope. The mirror operation captures a complete generation of the corpus: every canonical path, including out of tree handoff and planning state that the deployment declares, with relative paths and empty directories preserved, bytes hashed into a SHA-256 manifest. The mirror's current pointer advances only after the copied bytes are read back and verified against the manifest. Prior generations are preserved; the mirror has no delete, purge, or destructive sync operation. Local capture and remote verification are separate receipts, reported separately, because "saved locally" and "verified remotely" are different facts and operations that blur them eventually lie about one of them. Live databases are refused as mirror sources: a consistent export must be obtained first, because a byte copy of a changing database is a corrupt backup that verifies beautifully.
2. Restore is deliberately narrow: into a new or empty directory only. There is no restore over the top of a live corpus, because the failure that makes you reach for restore is exactly the failure that makes overwriting your only other copy unforgivable.
3. The verify operation checks every file in a saved generation against its manifest, and doctor inspects the local installation without changing it. Together with latest, which reads source events directly for recovery when index state is in doubt, these form the system's "trust nothing, check the files" toolkit, and they are the commands operators actually reach for at 2 AM.
4. A companion tool in the reference deployment, a writer directory generator, regenerates a directory of the agents who write to the spine: it scans the corpus, counts each known writer's tagged and mentioned presence per category, and republishes the directory data into the deployment's status displays. It exists because a shared memory needs a map of its authors as much as of its contents: provenance you cannot enumerate is provenance you cannot audit. The directory honors the corpus's provenance tag convention (section 8.2), counting an entry for its tagged author regardless of mentions.

### 7.4 Integrity failure modes, quarantine, and the November 2026 incident

1. The failure modes the design anticipates, in ascending order of seriousness: a stale index family (remedy: rebuild that family); a missing or damaged derived artefact (remedy: rebuild, since derivation is total); a malformed legacy file (indexed as text or flagged, no event guarantees claimed); and a stored event whose digests do not verify (remedy: none automatic; this is the loud stop of section 4.4).
2. The practiced response to the loud stop is quarantine. The offending file is moved, intact and unedited, to a quarantine location outside the corpus tree. The corpus returns to service. The file's contents are preserved exactly, because the file is evidence: whether it was damaged by a crash mid write, a tool that rewrote it, or a hand edit, the diagnosis starts from the bytes as found. Repair, when it happens, is a human ruled operation that ends with revalidation, never a background process that quietly rewrites history until the hashes pass.
3. The November 2026 incident, in the reference deployment, is the case study. A single hourly entry was written with a header whose stored payload digest did not match the digest its body computes under the current validation scheme. The effect followed section 4.4 exactly: collection failed corpus wide, the index stayed at its previous generation, and the corridor could not certify its own state until the file was quarantined. The follow on repair work was itself interrupted more than once by circumstances outside the corridor, which compounded the lesson: the system's gap was not detection, detection worked instantly and correctly, but tolerant diagnosis. No existing tool could walk the corpus, step over the one bad file, and report "exactly this one, exactly this class, everything else verified". Every tool either trusted the corpus wholesale or died on the same record the collector died on. That gap is the integrity crawler of section 12, and it is why that proposal is ranked first in value among the 0.3.2 components.
4. A second, quieter lesson from the same period: an index generation stuck behind the corpus is staleness, and staleness and corruption present identically in casual prose ("the corridor is behind", "the corridor is broken") while needing opposite responses. The system's diagnostics already separate them; its operators' language had to learn to. Section 12's crawler reports the two in different words for exactly this reason.

### 7.5 What operations deliberately does not do

1. Nothing in the system schedules itself. Capture, rebuild, mirror, and verification happen when an operator or an integrating host invokes them. The public CLI states the boundary in its own help text: nothing schedules autonomous work, publishes, or grants authority. A hosted agent's memory discipline is therefore an integration property, not a package property: the host must call capture after meaningful decisions, corrections, results, and task transitions, and must call recovery at session start. Section 8 describes the reference deployment's version of that discipline.

### 7.6 Version history, as far as the sources support it

1. The 0.1 and 0.2 era established the architecture this paper describes: the four arms, Reciprocal Rank Fusion at k of 60, the graph arm's specificity weighting, bi-temporal validity, and the multiplicative re-rank, over the file spine, with indexes cached as local files and JSON. The surviving development snapshot is version 0.2.0. Its validity closure still carried the heuristic experiment described in section 5.2, and its semantic arm's per call behavior was the impracticality 0.3.1 later fixed. The public record of this era is thin by the project's own admission: an early public changelog claimed version 1.0.0 while the package metadata reported 0.2.0, an inconsistency the 0.3.0 line corrected in the open. The lesson is recorded here because it shaped the project's current habit of letting the package, not the prose, be the version authority.
2. Version 0.3.0, publicly released 2026-10-11 under the MIT license, is the retention repair: category scope aliases repaired across collection, indexes, recall, and the CLI; source content and scope validated on recall, with root memories and full text included; heuristic fact suppression replaced with explicit timestamped supersession; durable idempotent events with handoff resume under revision checks and verified readback; immutable, non deleting mirror generations with pending receipts and restore; an installed hmc command line; and an optional, explicitly reported PageRank fallback when the graph dependencies are absent. It also generalized the collector from the reference spine's layout to any Markdown directory with auto detected categories, and moved the index cache to its current home. Where this paper describes the system generically enough to cover both the private deployment and the public line, it is usually describing a decision this release made.
3. Version 0.3.1, the live install in the reference deployment since its cutover on 2026-10-23, is a focused repair of the semantic arm and of cutover safety: recall reuses the verified built semantic generation instead of re-embedding the corpus per call, verified on the real corpus with zero document re-encodes on a fresh process recall. Its cutover history is instructive and is recorded in the deployment's operational notes: the first attempt rolled back because the new version's vector store library could not read the previous version's store, so the old store was moved aside, intact, and the new version built its semantic generations fresh. Nothing was deleted, the rollback path was preserved, and the incident is a small working example of the paper's larger claim: because the files are the truth and every derived artefact is regenerable, a failed derived store is an inconvenience, never a memory loss.
4. Version 0.3.2 is section 12: proposed, unbuilt, and the first version whose headline feature is not retrieval at all, but the persistence of retrieval's own evidence.

## 8. Governance: many writers, one spine

### 8.1 The writing contract

1. The reference deployment runs many agents against one corpus, and its governance is a contract rather than a permission system. The contract, stated generically: check the corridor before acting on anything that prior work touches; write an entry after any significant decision, correction, or completion; link every correction to the entry it fixes; tag every entry with its author's identifier; and never act from vague recollection when a written record exists. The last clause is the one with teeth. The system's founding operational failure mode was not bad retrieval. It was agents proceeding from a summary of a summary while the full record sat unconsulted in the corpus.
2. Capture points are transitions: a decision made, a result verified, a task delegated or completed, a correction learned. The integration contract the public line documents says the same thing from the host's side: record consequential intent before execution and outcome afterward, so that an interruption leaves an inspectable trace rather than a mystery; update the resume block at the same transitions; and before any context compaction or session restart, flush pending state and verify readback, then on restart load the resume and the latest events for the active task before reaching for deeper recall.

### 8.2 Provenance

1. Every stored event names its actor with a full identifier, and periodic entries carry an author tag line under the title. Provenance is not decoration: it is what lets a reader weight a record (a verified result reported by the agent that ran it outranks a second hand summary), what lets the writer directory (section 7.3) enumerate authorship, and what lets a correction be routed to the author of the thing corrected. The corpus treats anonymous memory as a defect for the same reason the store treats unverified capture as a defect.
2. Equally, provenance is not authority. The public architecture states that memory content does not grant execution authority, and the resume block's contents are data, never an authorization. A recorded statement that something was approved is evidence about the past. It is not a standing permission slip, and the system's operators are expected to keep that distinction bright, because a memory system that quietly becomes a permission system has failed in the most dangerous direction available to it.

### 8.3 The correction protocol

1. Corrections follow a fixed shape: a new entry, written promptly, that states what was wrong, what is right, and why, and that names the superseded record so the validity layer can close its window. A correction that exists only in prose, without the supersedes link, is treated as unfinished work (section 5.4). Corrections are recorded with their resolutions at equal weight to the original claim: a corpus that remembers errors vividly and resolutions faintly trains its readers, human and agent alike, to distrust settled facts, which is its own failure mode.
2. When the user of the reference deployment states that something is resolved, done, or changed, that statement is current truth and the record is updated from it immediately. Files describe the world as last verified; the operator's word is a verification event, and the corpus's job is to catch up to it, not to argue with it.

### 8.4 Read discipline

1. Reading has a protocol too: run the corridor lookup first, read the latest entries in the relevant category, check the category index for quick facts, and only then fall back to looser notes and recollection. Results are opened at the source before being acted on, because a summary of an entry is a claim about the entry, and the corpus exists precisely so claims can be checked against records.
2. An empty result is never treated as proof that nothing was recorded. The public architecture is explicit: capture receipts establish that something was stored; an empty recall establishes only that this lookup, with these arms, in this scope, found nothing. The recovery path for doubt is latest events and the category index, not a shrug.

## 9. Evaluation: what can be measured today, and what cannot

### 9.1 What the system measures about itself

1. Every lookup's diagnostics receipt (section 6.8) is a measurement: generation digest, eligible and excluded counts, per arm health. Aggregated over time, these answer operational questions precisely: how often the graph arm falls back, how often the temporal arm abstains, how much of the corpus validity currently excludes, whether results came from the current generation or a stale one.
2. The test suites measure correctness of mechanism on synthetic data: unit and integration tests cover the validity windows, the PageRank ranking, the re-rank arithmetic, idempotent capture, resume block revision handling, and mirror verification, in isolated directories with no personal memory, no network, and no model downloads. Optional semantic behavior is tested against explicitly identified fakes, and the project is careful to say those are not live backend benchmarks.
3. The reference deployment adds operational evidence of a blunter kind: the corridor has run as the daily memory for a multi agent operation since its first versions, the corpus has grown past 2,900 entries under real write load, and its failures (a corrupt record halting collection, a semantic generation that had to be rebuilt across a version cutover, index generations lagging the corpus) were all detected by the system's own diagnostics rather than discovered by accident. Detection is not prevention, and this paper does not present uptime anecdotes as benchmarks. It presents them as evidence the instrumentation points at real failures.

### 9.2 Known behaviors, stated as behaviors

1. Consensus ranking favors the broadly supported entry. In practice this means operational lookups (a name, a decision, a status) resolve reliably, while a question whose true answer lives in exactly one oddly worded entry depends on that entry winning one arm decisively or on the operator widening top_k.
2. Validity filtering before ranking measurably changes results in corrected domains: superseded entries vacate arm slots, so current facts in heavily corrected areas rank higher than they would under post filter designs. This is observable in diagnostics as the excluded count, and it is the behavior the design most intends.
3. The recency factor is gentle by construction (section 6.7). It breaks near ties toward the present. It does not rescue a current fact that no arm found, and it is not a freshness guarantee: freshness comes from the source reread and the generation keys, not from the decay curve.
4. Dedup mode finds twins the default path misses, for the structural reason given in section 6.6. The reference deployment's periodic duplicate checks have consistently surfaced a small number of candidates, most of them intentional carry forwards of standing items across periodic entries, handled by the validity layer rather than by deletion.
5. The semantic arm's opt in status has a measurable consequence: default lookups are fast and model free, and paraphrase recall is available exactly when an operator judges the question needs it. The cost is a discipline cost: an operator who never opts in owns a three arm system. The diagnostics make that visible on every receipt, which is the system's chosen mitigation.

### 9.3 What cannot be claimed today

1. There is no public relevance benchmark for this system: no labelled query set, no recall at k figures against a ground truth, no comparison harness run against the systems in section 10 on identical corpora. Statements in this paper about retrieval quality are mechanistic (what the arithmetic does) and operational (what the deployment observes), and are labelled as such. A reader who needs benchmark numbers should treat their absence as the honest state of the project, and section 11 lists building the harness as open work.
2. There is no measured latency profile published for the live corpus across hardware. Full rebuilds are minutes scale on the reference machine; per lookup cost is dominated by the source snapshot and graph construction over the snapshot, and both grow with the corpus. Section 11 takes up the scaling consequence directly.
3. The graph arm's entity extraction quality is unmeasured as extraction: no precision or recall figures exist for the heuristic extractor against human judgement on this corpus. Its failures are of a known kind (missed entities that are lowercase, oddly cased, or purely numeric; spurious entities from capitalized prose), and the specificity weighting blunts the spurious side, but unmeasured is unmeasured.

## 10. Related work, positioned honestly

1. Hindsight (Vectorize). The four arm retrieval architecture and the Reciprocal Rank Fusion implementation are adapted from Hindsight, and the project says so in its README, its architecture document, and a dedicated credit file. The corridor's divergence is subtraction: where Hindsight runs a database backed service with language model fact extraction and consolidation, the corridor keeps plain files, skips per write model calls entirely because its entries are already structured, and replaces the consolidation engine with explicit supersession plus dedup mode. The borrowed insight is that rank fusion over diverse arms beats any single arm. The unborrowed cost is the operational weight the corridor declines to carry.
2. HippoRAG (OSU NLP Group). The graph arm's Personalized PageRank over an entity and document graph, with specificity weighting, adapts HippoRAG's retrieval pattern, itself inspired by hippocampal indexing theory: entities as the index, documents as the content the index points at. The corridor's graph is cruder than HippoRAG's (heuristic extraction, co-occurrence edges, no passage level graph construction by a model), and the paper claims the pattern, not parity.
3. Graphiti (Zep). The bi-temporal validity model, facts with valid and recorded intervals closed by later facts, references Graphiti's design. Graphiti maintains a temporal knowledge graph with entity resolution and hybrid search over graph, vector, and keyword signals, backed by a graph database. The corridor takes the temporal semantics and leaves the graph database, the entity resolution, and the service architecture behind: its validity lives in an index over files, its entities are strings, and its corrections are explicit IDs rather than resolved edges. For corpora at this scale the trade has held. At larger scale or with messier write discipline, Graphiti's machinery exists precisely because explicit discipline stops being enough, and section 11 says so.
4. mem0. The multiplicative re-rank pattern (fusion score times importance times recency) follows mem0. mem0 as a system is a managed memory layer with model driven extraction and update decisions against existing memories. The corridor borrows the arithmetic and declines the update model: nothing in the corridor lets a model decide that an existing memory should change.
5. MemPalace. MemPalace is a neighboring system in the same problem space, organizing memory into a spatial palace structure for agent recall. The corridor's public documentation mentions it for one precise reason: to state a non fact. The corridor's semantic store is sometimes assumed to connect to MemPalace automatically. It does not; no bridge is included, and the two systems' stores are separate. They are alternative answers to the same dissatisfaction with session bound memory, differing in metaphor and mechanics: a palace of placed memories versus a corridor of filed, hashed, correctable events with hybrid retrieval over them.
6. Generic vector RAG. The baseline the corridor defines itself against: chunk the notes, embed the chunks, retrieve by similarity, generate. Section 1.3 gives the full argument. In one line: vector RAG answers "what text resembles the question", and agent memory needs "what is currently true, what was true then, what did we know then, and show me the record", which are retrieval, validity, and provenance questions that similarity alone cannot phrase, let alone answer.
7. Agent observability and trace tooling (LangSmith, Langfuse, and the spider artefacts of section 12) are related to the roadmap, not to the current system, and are positioned there.

## 11. Limitations and open problems

1. Per lookup cost grows with the corpus. Recall rereads the source snapshot and rebuilds graph state per snapshot in the current implementation. At roughly three thousand entries this is entirely workable. At thirty thousand it will need the journal driven incremental collection the public architecture already names as future work. The design's freshness guarantee (section 6.0) is bought with this cost, knowingly.
2. Heuristic entity extraction is the weakest component by construction. It misses entities, invents entities, and knows nothing of identity: two people sharing a name are one node, and one person under two names is two nodes. The specificity weighting and the fusion's consensus requirement keep this from dominating results, but a corpus whose questions turn on fine entity distinctions will outgrow the extractor before it outgrows anything else.
3. Validity completeness is a human discipline with machine enforcement only at the link level. Unlinked corrections (section 5.4) are the standing risk, and the mitigation is cultural (section 8.3) plus periodic duplicate and consistency review. The system detects the symptom class; it cannot close the gap itself without becoming the kind of inferred truth machine section 2 forbids.
4. Broken supersession links are invisible today (section 5.4). This is a known, named defect with a proposed remedy (section 12), listed here so the limitation and the roadmap cannot drift apart.
5. The event layer and the legacy layer coexist. Plain Markdown entries carry no digests, no idempotency, and no explicit validity. Retrieval treats them as text. A corpus that migrates gradually, as the reference corpus did, lives with two truth standards at once, and its operators must know which class a given record belongs to before leaning on it.
6. Local locks are local. Multi machine writing is handled by mirror generations and operational convention, not by the store. Two writers on two machines editing against the same corpus tree through a synced folder is outside the design envelope, and the documentation says so rather than discovering it for the user.
7. No relevance benchmark exists (section 9.3). Building a labelled evaluation set for a personal operational corpus is genuinely hard (the ground truth is the operator's judgement, and the corpus contains material that cannot be published as a benchmark), but without one, quality claims stay mechanistic. A synthetic corpus harness with planted corrections, paraphrases, and time shifted questions is buildable and is the obvious next evaluation step.
8. The semantic arm's generation discipline protects against model and document set drift, at the price of full rebuilds when either changes. There is no incremental embedding path in the live install.
9. Memory is not authority, and the system cannot enforce that distinction (section 8.2). It can only refuse to blur it in its own documentation and receipts. Deployments that wire recall output directly into action without a verification step are misusing the tool in a way no retrieval feature can prevent.
10. Finally, the system's deepest limitation is the one it shares with every memory system: it can only retrieve what was written. The corridor's answer is procedural (the writing contract of section 8) rather than technical, and this paper regards that as the correct allocation. Capture discipline is a practice. Retrieval is a mechanism. Confusing the two produces systems that are excellent at finding the gaps in a memory nobody kept.

## 12. Roadmap

### 12.1 Version 0.3.2, proposed and unbuilt: the spider

Status, stated before anything else in this section: 0.3.2 does not exist. Nothing in this section describes built, tested, or released software. It is a design proposal with an evaluation behind it, included because it is the corridor's next planned increment and because its central finding reflects back on the current system: most of what 0.3.2 would add already happens inside every 0.3.1 lookup, and is thrown away.

1. The finding. Fusion already computes, per candidate, its rank in each arm and each arm's raw score. Recall already computes the health receipt. PageRank already computes a score for every entity node in the graph, and the extraction loop discards every entity score, keeping only documents. Validity already maintains the full supersession map, while default recall surfaces only a count of what it excluded. The provenance of a lookup, in other words, is computed in full and persisted nowhere. The stepped over candidates past the top_k cut, the activated entities, the excluded predecessors: all transient.
2. The proposal. Give the retrieval system a body and keep its footprints. In the design's governing image, borrowed from two spider artefacts that circulated in October 2026 (section 12.2), the spider is the semantic arm, embodied: MiniLM vectors pick the first foot plants, the closest entries to the query. The graph walk is the legs. The record the walk leaves behind, steps, scores, mechanical connection reasons, and superseded entries stepped over, is the web. Concretely, 0.3.2 would add:
   1. A versioned trace record (working name helix-trace/v1) emitted when tracing is requested for a recall: the query (redacted before any export), scope, as_of and known_at, the source generation digest, per arm status and step lists (entry ID, arm score, arm rank, and for the graph arm the seed entities and a capped activation summary, top 50 entities), the fused candidate list before the cut with its re-rank factors, the stepped over set (the full validity excluded set in scope, with supersession data, labelled as the full set), the final result IDs in order, and a count of redactions applied. Traces are stored outside the corpus, because a trace is a record about memory, not a memory, and a spider that walks its own footprints as memories would corrupt retrieval within weeks.
   2. A crawl map renderer: one self contained HTML file per trace or trace set, interpretation living in the renderer only. Steps whose entries have since been superseded, or whose generation has gone stale, render as released feet: present, dimmed, with the reason shown, never silently re-anchored to a successor. The trace stores facts; the renderer interprets; that separation is taken directly from the prior art's best discipline.
   3. A redaction module for trace free text, implementing a known rule list (private key blocks, credentialed URLs, known token formats by prefix and shape, authorization headers, secret named flags and assignments, with exemptions for reference style values), plus the stronger structural rule that trace records carry identifiers, scores, and reasons, never document body text.
3. The integrity crawler, the component ranked first in value. The same walk, run over the whole corpus instead of one query, becomes a read only audit: it walks the file tree itself (never through the collector, which by design dies on the first malformed record), opens each file independently, and reports per file failures as findings instead of exceptions. Its checks, specified against the live formats: header and digest integrity for stored events; broken supersession links, enumerated with the source record's validity state, closing the blind spot of section 5.4; three orphan classes reported separately (on disk but not indexed, referenced but no file behind it, and a periodic entry with no paired handoff, the last labelled as a convention check rather than a format check); stale generation comparison per index family, reported as staleness in those words, not corruption; and handoff resume block validation run as a check rather than a fatal error. Its output is a report only: findings grouped by class and severity, plus the corpus digest before and after the crawl, required to match, proving the crawl changed nothing. It never repairs, quarantines, or rebuilds. Repair stays a human ruled action, as it was in November 2026.
4. Invariants the proposal binds itself to: tracing on or off, a lookup returns identical results in identical order with identical scores; no language model anywhere in the trace path, so no generated prose ever appears inside a provenance artefact; no writes to the corpus by any spider component; tracing opt in per invocation or session, never always on, with exports explicit and never mirrored by default, because a trace corpus is a query corpus and queries to a personal memory are sensitive text; graph activation capture capped, reusing computed values, never recomputing the walk for the trace's sake.
5. Evaluation for the proposal is specified as fixtures, not aspirations: an invariance test over golden queries; the quarantined November 2026 record as the corrupt fixture (the crawl must report exactly one digest class finding naming it, complete, and print matching before and after digests, while ordinary recall over the same sandbox corpus is expected to fail at collection, proving the crawl is not collector based); a broken link fixture; a three generation supersession chain traced at the middle period; a stale family fixture; the three orphan fixtures; redaction seeds including one formatless secret expected to survive, proving the limit is documented rather than discovered; a full corpus performance run with a hard requirement that the crawl load no embedding model; a release and re-anchor rendering test; and a self reference test proving traces and crawl reports are never counted as corpus files.
6. What is explicitly out of the 0.3.2 scope: any change to retrieval results; any deployment of the corridor to a second host as part of this work; any copied code from the spider artefacts (clean implementation from the specification, licenses checked); and any public release step bundled with the build. Release follows the standing pipeline separately, on explicit approval, when there is something tested to release.

### 12.2 Prior art for the spider design

1. Spiderling (Elias Hridoy, MIT licensed): a VS Code extension whose spider crawls code while coding agents work, distilling sessions into a replayable trace (schema spiderling.agent-trace/v1) of steps carrying paths, counts, line ranges, and the agent's own one line captions, never file contents. Its transferable contributions are the distilled event discipline, the rule that the reason beside a step is quoted from the actor or stated mechanically, never invented; the separation of trace (facts) from analysis (interpretation, kept in the viewer); its drift thresholds, offered by its own code as things worth a second look, not verdicts; its redaction rule classes; and its single self contained HTML export. Its phase inference is heuristic over names and command shapes and is not transferred: the corridor's analogue phases (seed, spread, fuse, filter, rank) are phases the code actually passes through. The extension itself is not adopted: it is bound to editor log formats this system does not produce, and its usage evidence is thin. The design takes its discipline, not its code.
2. Web Crawlers (Slava Rybin, and the open source clone by cyohei9907): a JavaScript and CSS spider that walks a live web page with its feet planted on real words and links, using two bone inverse kinematics; an accompanying browser extension releases the spider on any page without modifying it. Its transferable mechanics: feet anchor to artefacts (a fractional position inside a live word's rectangle), not to coordinates; the release rule, a foot whose artefact moves beyond a threshold (14 pixels of Manhattan distance in one frame, in the original) lets go and stays, rather than being dragged; the non mutating overlay discipline of the extension (a closed shadow root, pointer events none, minimal permissions, no network); and its frame discipline (reads only during update and draw, one queued write commit), which translates into the trace write discipline of section 12.1: accumulate in memory, flush once, never let tracing change the timing shape of recall. Rejected for this system: the demo's glitch mutations, in which a planted foot alters the word it touches. A memory spider's feet mark. They never mutate.
3. The wider field, for calibration: Personalized PageRank memory retrieval is HippoRAG's, bi-temporal validity is Graphiti's, rank fusion with per arm provenance is the Hindsight pattern, and agent tracing with replay is established practice in the LangSmith and Langfuse line. No component of 0.3.2 is novel, and the project claims none. The composition is the contribution: a per lookup replayable trace of the memory system itself rather than of an agent's tool calls; superseded entries as first class trace objects, rendered with their validity windows projected at the lookup's known_at, so the web shows what the system believed at the time; and the same instrument doubling as an integrity crawler over a hash chained event store. A novel composition of known parts, stated as a product difference, not a research claim.

### 12.3 Further possibilities, unnamed and unpromised

1. A small local model as a suggestion layer over crawl and trace findings: proposing which findings deserve a human ruling, drafting correction links for approval, never writing, closing, or pruning anything itself. The corridor's own experiments counsel patience here: a larger local embedding candidate was benchmarked against MiniLM during the system's development and set aside as several times slower with no clear quality win, and production stayed on the small model. Any future model layer inherits that evidence bar.
2. A platform tracking variant of the trace: the same event core (timestamp, actor, operation, target, reason, result) applied to observations of an agent operations host from the memory host, feet landing only where a verified read actually returned content, absences recorded as released feet with reasons. It reuses the schema; it does not move the corpus, and no second corpus is created on the operations host. Sequenced after the corridor trace proves the schema, not before, because the operations data is the noisiest data available to test against.
3. Incremental collection and incremental embedding, when corpus growth makes the current full snapshot costs bite (section 11, item 1 and item 8), designed against the same generation discipline so freshness guarantees survive the optimization.
4. A synthetic evaluation harness (section 11, item 7): planted facts, corrections, paraphrases, and time shifted questions over a synthetic corpus, giving the project its first labelled relevance numbers without publishing a single real memory.
